# 锁步联机与动态帧率补偿

> 适用场景：模组里出现 `autoTrigger` 高频判断、每帧位移、`teleportPoint`、`buildtime` 配动画、
> 用贴画做运算动画 —— 任何"每帧推进一点"的逻辑，在联机下都可能出问题。
>
> 本文分两部分：**社区经验**（来自西瓜十三号，2026-10-17 讨论）和**引擎核实**（反编译 `game-lib.jar` 得到）。
> 两者结论冲突时以核实为准，但经验部分指出了真实踩过的坑，不要因为没核实就忽略。

---

## 一、问题从哪来：锁步（lockstep）

铁锈的联机是**锁步**：所有客户端跑同一套模拟，只同步玩家指令，不同步单位状态。
只要两端的模拟结果有一帧不一致，后面就会越差越远 —— 这就是**不同步（desync）**。

锁步对模组的要求很硬：

1. **同一帧、同一输入 → 必须得到同一结果。**
2. **每帧做的事必须一样多。** 一端多跑一次判断、少跑一次，状态就分叉。
3. **不能依赖渲染帧率。** 渲染快慢是客户端自己的事，模拟帧率才是共享的。

## 二、30 帧基准与补偿系数

### 2.1 基准从哪来

社区经验：**理想状态下最高运行速度是 30 帧；高于 30 帧，多人同步下很可能会出现不同步，或行动被吃掉。**

这里的 30 是**社区约定的基准值**，不是我从引擎里读出来的常量。
（反编译里能看到 `* 16.666666f` 这类秒↔刻换算，暗示内部刻度接近 60 Hz；
但"多人模拟的有效帧率"受游戏速度设置和锁步节奏影响，不能直接等同。
**所以 30 只作为基准用，不要当成引擎常量引用。**）

### 2.2 补偿公式

若某个动作在基准帧率下每帧推进 `step`，实际帧率是 `F_action`，则：

```
C = 30 / F_action          # 帧率补偿系数
每帧实际推进 = step * C
```

例如每帧前进 10 米，帧率是 15，则 `C = 2`，每帧应前进 20 米。

### 2.3 最关键的一条：F_action 必须实测

> **不能把渲染 FPS 当服务器帧率。**

`F_action` 是**这个动作真实被调用的频率**，它由三件事共同决定：

1. 引擎模拟帧率（受游戏速度设置影响）
2. `autoTriggerCheckRate` 的档位
3. 这个动作自己的 `autoTrigger` 条件多久成立一次

`autoTriggerCheckRate` 的合法值（从枚举 `<clinit>` 读出，不是猜的）：

| 值 | 含义 | 若模拟帧率 = 30，动作频率 |
|---|---|---|
| `everyFrame` | 每个模拟帧都检查 | 30 Hz |
| `every4Frames` | 每 4 个模拟帧检查一次 | 7.5 Hz |
| `every8Frames` | 每 8 个模拟帧检查一次 | 3.75 Hz |

**只有这三个值，没有 `everySecond`。** 写别的会解析失败。
注意这里的 "frame" 指**模拟帧**，不是渲染帧。

**推论**：`F_action` 通常远低于 30。用了 `every8Frames` 就是 `30 / 8 = 3.75`。
用错档位，补偿系数就会整体偏大或偏小 —— 这比不补偿更糟，因为它看起来"动了"，但动得不均匀。

## 三、怎么测 F_action：能量恢复探针

社区给的办法：**用原生的能量恢复速度来反推模拟帧率。**

思路是：原生能量恢复是引擎按固定节奏推进的，把它当成"节拍器"来观测。

**但必须注意两点**（这条是提醒，不是否定）：

- **它给的是"模拟时间推进速度"，不是渲染 FPS。** 这正是我们要的，但别拿它去和屏幕帧率对比。
- **没有独立时间基准时，不能直接由它推出真实帧率。** 你只能得到"相对基准的比例"。
  要拿到绝对值，还得有一个已知时长的参照（例如游戏内计时器、或一次固定 `buildtime` 的耗时）。

**推荐做法**：不追求绝对帧率，只追求**比例**。

```
让单位在已知时长 T 内恢复能量，记录恢复量 E
在基准环境下同样操作，记录 E0
C = E0 / E
```

这样得到的 C 直接可用于补偿，且不依赖你对绝对帧率的判断。

## 四、补偿带来的四个副作用（都是真的）

补偿系数不是免费的。系数越大，副作用越明显。

### 4.1 位移放大 → 穿透与判定问题

`teleportPoint` 乘上 C 之后，一帧的位移变大。

- 子弹/投射物可能出现**穿透**（一帧跨过了目标）
- 平滑运动可能"跳格"，看起来不连续

**缓解**：位移类补偿要设上限；超过上限就分多帧走，而不是一帧走完。

### 4.2 检测半径没跟着放大 → 中间的目标被跳过

这条最隐蔽：

> 如果同时执行"判断周围敌人并传递信息"，补偿系数过大可能导致**中间的敌人被忽略**。

原因很直白：你这一帧前进了 `10 × C` 米，但检测半径还是原来那个值，
于是这段距离里被跨过的敌人**从来没进入过检测范围**。

**两种缓解**（社区给的方向）：

1. **动态检测范围**：半径也乘 C（或按 C 开方，避免范围爆炸）
2. **用附属单位做检测**：沿路径撒几个不可见的附属单位，各自检测一小段

选哪个取决于你对性能的容忍度：方案 1 便宜但范围会变大（可能误伤友军判定）；
方案 2 准确但要管一堆附属单位的生命周期。

### 4.3 贴画动画卡顿

> 这东西直接影响根据运算来实现的贴画动画帧，很可能会出现明显卡顿的动画。

贴画动画（`decal_*` 的 `frame` / `animateFrameSpeed`）如果是靠逻辑每帧改 `frame` 驱动的，
帧率一变，动画速度就变；补偿之后又会在某些帧跳格 —— 表现就是卡顿。

**建议**：能用原生 `animateFrame*` 的地方就别用逻辑驱动。原生动画由引擎按时间推进，天然免疫帧率问题。

### 4.4 `buildtime` 与动画不同步

> 如果你想用 `buildtime` 行动配合动画实现某个动作，可能在多人模式下**行动先结束但动画还没结束**。

`buildtime` 是按模拟时间走的，动画是按渲染时间走的。两者在掉帧时必然错位。

**缓解**：不要用"动画播完"当行动结束条件；反过来，用行动结束去**强制跳到动画末帧**。

## 五、引擎侧已核实的事实

下面这些是反编译 `game-lib.jar` 读出来的，可以直接当依据用。

### 5.1 `rnd()` 不是随机数

这条和联机直接相关，但结论和直觉相反：

`LogicNumberFunction$FunctionRnd.readNumber` 的实现，一句话说完：

> 把 `randomIndex + unit.bC` 当作 seed，传给内部的整数取模函数；
> 那个函数先取全局种子 `l.bJ`，再用 seed 和 `l.bx` 做几轮乘加混合，最后对 `range` 取模。

关键点不是那串乘加常数，而是**混进去的只有三样东西**：全局种子、解析期分配的调用点序号、单位自身的 `bC` 字段。
没有时间、没有坐标、没有每帧变化的量。

- `l.bJ` 是**全局种子**，开局设定后不再变（`i.java:615`：`this.bJ = this.bX.ay.q;`）
- `randomIndex` 是**解析期分配的调用点序号**（同一个 `rnd()` 写法永远是同一个序号）
- `unit.bC` 是该单位的一个字段（创建时确定）

**结论**：

1. **`rnd(0,10)` 对同一个单位、同一个调用点，永远返回同一个值。** 它不是"每次调用重新掷骰子"。
2. **它天生联机安全** —— 只依赖全局种子和单位字段，两端锁步下必然一致。
3. **想要变化，必须自己换种子**：把 `self.timeAlive` 或某个变化的量塞进参数里，例如
   `rnd(0, 10 + self.timeAlive % 3)` 之类的写法，而不是指望它自己变。

这一条解释了为什么很多模组的"随机"效果看起来是固定的 —— 不是引擎的 bug，是用法问题。

### 5.2 `tookDamage` 在扣血之前触发

伤害结算方法里，`tookDamage` 事件在真正扣血的那一步（`super.a(...)`）**之前**发出。

所以在 `tookDamage` 里读 `self.hp` 拿到的是**挨打前**的值。做伤害差分恒为 0。
联机场景下更要注意：别在事件里做"根据掉血量决定后续"的判断。

### 5.3 `alsoTriggerActionRepeat` 必须配对

`repeat` 嵌在 `alsoTriggerAction` 的解析分支里，单独写无效；
`repeat: 0` 不是"不重复"，而是把整个派生动作**取消**。

对帧率补偿的影响：如果你用 `repeat` 实现"一帧分多步走"，
`repeat: 0` 会让整段逻辑静默消失 —— 表现为单位原地不动。

## 六、写联机模组前的检查清单

逐条过一遍，任何一条打不了勾，联机就有风险。

- [ ] 我的逻辑**不依赖渲染帧率**（没有拿画面帧数做判断）
- [ ] 我确认了 `F_action` 的**实测值**，不是假设值
- [ ] 我用了 `autoTriggerCheckRate`，并知道档位只有 1 / 1/4 / 1/8 三档
- [ ] 所有"每帧推进"的量都乘了补偿系数 C
- [ ] 位移补偿有**上限**，不会一帧穿过目标
- [ ] 检测半径跟着补偿**一起放大**（或改用附属单位分段检测）
- [ ] 贴画动画优先用原生 `animateFrame*`，不是逻辑驱动
- [ ] 没有用"动画播完"当行动结束条件
- [ ] 随机效果**没有**依赖 `rnd()` 自动变化
- [ ] 没有在 `tookDamage` 里读 `self.hp` 做差分
- [ ] 没有跨 mod 引用文件（见下）

## 七、另一个和联机无关但同样致命的坑：跨 mod 不能读文件

铁锈**不允许一个 mod 读另一个 mod 的文件**。所以：

- 通用模板改了之后，**必须手动覆盖到每一个分包**（Main + 各 DLC）
- 不能靠"引用主包里的模板"来省体积
- 音乐/音效**只在一个包里放**，否则体积翻倍（这条是体积问题，不是功能问题）

这也是为什么大模组里同一份模板会重复出现好几遍 —— 不是作者偷懒，是引擎限制。
