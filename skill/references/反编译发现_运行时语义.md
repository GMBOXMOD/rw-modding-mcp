# 反编译发现的运行时语义

用 CFR 0.152 把 `game-lib.jar` 反编译成 Java 源码后，读到的**实现层面事实**——这些在代码表、维基、任何指南里都查不到，只能读源码。

> 本文只记录**结论和定位**，不收录反编译源码（见仓库 `.gitignore` 的政策）。
> 要自己复核，按下面「怎么复现」跑一遍，然后照「附：反编译源码的位置」去读。

## 怎么复现

```bash
# 1. 下载 CFR（单 jar，2 MB）
curl -L -o tools/jar/cfr.jar \
  https://repo1.maven.org/maven2/org/benf/cfr/0.152/cfr-0.152.jar

# 2. 反编译（1698 个 class，约 60 秒）
java -Xmx2g -jar tools/jar/cfr.jar \
  "D:/steam/steamapps/common/Rusted Warfare/game-lib.jar" \
  --outputdir tools/jar/src --silent true
```

输出在 `tools/jar/src/`，1698 个 `.java`。类名被混淆（`ag` / `j` / `d`），但控制流和字符串常量完整可读。

## 发现一：`setUnitMemory` 的多赋值是**严格顺序执行**

**这条最重要。** 它决定了"先算再用"的写法能不能成立。

`VariableScope$CachedWriter.writeToUnit()` 的实现就是一个循环：遍历内部的 writer 列表，**逐个**调用 `writeToUnit`。没有并行求值，没有先算后写。

**含义**：`setUnitMemory` 里逗号分隔的赋值，按书写顺序一条条生效，后面的表达式能看到前面刚写入的新值。

所以这种写法是**正确的**：

```ini
# 先减仇恨，再根据"减完的新值"决定要不要清空槽位
setUnitMemory: """
threat_value[memory.i]= max(0, memory.threat_value[memory.i] - 40),
threat_units[memory.i]= select( memory.threat_value[memory.i] <= 10, null, memory.threat_units[memory.i] )
"""
```

如果是并行求值，第二行会读到旧值，槽位就永远不会被清空——**逻辑悄悄失效，且没有任何报错**。

同理，伤害差分也依赖这个顺序：

```ini
# 先用旧 hp_prev 算出伤害，再更新 hp_prev
setUnitMemory: dmg= max(0, memory.hp_prev - self.hp), hp_prev= self.hp
```

## 发现二：`isVisible` 写进 `[hiddenAction_*]` 会**加载期抛异常**

`ag.java` 第 2662-2666 行，解析 action 节时：

- 如果当前节是 hiddenAction，且 `isVisible` 不是静态 `false` → 直接抛
  `"[节名]isVisible doesn't make sense to use in hidden actions"`
- 否则把可见性**强制**置为 `false`

**规则**：
- `[hiddenAction_*]` 里**不能**写 `isVisible`，除非值是静态 `false`
- 写了 `isVisible: if ...` 或 `isVisible: true` → **加载时报错，整个模组起不来**
- `[hiddenAction_*]` 的可见性被强制设为 `false`——这是它的定义，不是可选项

这是少数"会明确报错"的错误，比静默失效好查。但知道规则能省一次重启。

## 发现三：`alwaysSinglePress` 单独用**不够**

`ag.java` 第 2648-2655 行，读这几个键并算一个内部标记：

| 键 | 默认值 |
|---|---|
| `canPlayerCancel` | **`true`** |
| `allowMultipleInQueue` | **`true`** |
| `alwaysSinglePress` | `false` |

只有 `!canPlayerCancel && !allowMultipleInQueue && alwaysSinglePress` 三者同时成立，才标记为"立即执行"。

**默认值是陷阱**：前两个都默认 `true`。所以只写 `alwaysSinglePress: true`，那两扇门还开着，行为不是你以为的那样。

**正确写法**：

```ini
[action_myButton]
alwaysSinglePress: true
allowMultipleInQueue: false
canPlayerCancel: false
```

三个缺一不可。

## 发现四：`alsoTriggerActionRepeat` 的三种取值都是陷阱

`ag.java` 第 2818-2831 行，读这两个键的逻辑是**嵌套**的：

1. 先读 `alsoTriggerAction`；值缺失或等于 `NONE` → 整段跳过
2. 只有上一步成功，才会去读 `alsoTriggerActionRepeat`
3. 如果 repeat 是**静态数字**：
   - `0` → **把 `alsoTriggerAction` 整个清空**（派生动作不执行）
   - `1` → 走优化路径，不设重复标记（就是普通的一次执行）
   - `≥ 2` → 记下这个重复次数
4. 如果 repeat 是**运行时表达式** → 直接记下，交给运行期判断

**三条规则**：

1. **`alsoTriggerActionRepeat` 单独写无效** —— 它嵌在"有没有 `alsoTriggerAction`"的判断里。
2. **`repeat: 0` 不是"不重复"，而是"把整个 `alsoTriggerAction` 取消"**。这是真正的反直觉陷阱：你写 `repeat: 0` 想表达"这次别重复"，结果是**派生动作整个不执行**。
3. **`repeat: 1` 走优化路径**，就是普通的一次执行。

**实用结论**：`alsoTriggerActionRepeat` 只有在 `> 1` 时才有"重复"语义；`0` 是禁用开关。写循环时别用变量算出 0。

## 发现五：`tookDamage` 在**扣血之前**触发

`j.java` 第 3926-3931 行，伤害结算方法的结构是：

```
1. 发出 tookDamage 事件（af.n）
2. return super.a(am2, f2, f3)   ← 真正扣血在这一步
```

**事件先发，血后扣。** 后果：

```ini
# 想用血量差分算这一下掉了多少 —— 永远得到 0
setUnitMemory: dmg= memory.hp_prev - self.hp, hp_prev= self.hp
```

事件触发时 `self.hp` 还是挨打前的值，`hp_prev - self.hp` 恒为 0。**而且不报错**——仇恨值系统会静默地永远不累积。

**能拿到伤害值吗？不能。** `eventData(...)` 读的是事件对象的变量作用域（`LogicBoolean.activeEvent`），而这里传进去的第三个参数是抛射体的颜色数组，不是伤害数字。

**替代方案**：
1. 按**攻击者体型**加权（`eventSource.maxHp`）—— 很多商业 RTS 的仇恨就是按威胁等级而非伤害算的。
2. 记 `pending = true`，下一个 tick 再比血量（代价：1 秒延迟，期间多次受击会被合并）。
3. 让攻击方用 `mutatorX_addResourcesDirectHit` 自己统计命中，再发消息告诉被攻击方。

## 发现六：CFR 对枚举的反编译**不可靠**，必须用 `javap -c` 复核

`af.class` 是事件枚举。CFR 把它渲染成 `enum af { a, b, c, ... r }`——**名字全丢了**。

用 `javap -c` 看 `<clinit>`，真实构造是 `new af("created", 0)`、`new af("tookDamage", 13)` 这种形式：
枚举常量的**字段名**是 `a`..`r`，但传给构造函数的 **name 是真实事件名**。
`Enum.name()` 返回后者，所以 `ab.a()` 里 `enum.name().equalsIgnoreCase("tookDamage")` 能匹配上。

**教训**：CFR 会丢掉枚举的 name 映射。凡是涉及枚举，一律 `javap -c <class>` 看 `<clinit>` 里的 `ldc` 字符串。

## 附：逻辑函数全集只有 27 个

`LogicBoolean.java` 第 318-345 行的注册表（`addBooleanType`）：

```
memory, self.readUnitMemory, eventData, self.playername, self.teamname,
debug, debugPassthrough, select, str, substring, lowercase, uppercase,
int, rnd, max, min, length, squareRoot, distanceSquared, cos, sin,

directionBetween, createMarker
```

**注意缺什么**：没有 `abs`、没有 `floor` / `round` / `pow` / `atan2`，也没有 `sqrt`（叫 `squareRoot`）。

- 取绝对值：`max(x, -x)`
- 开方：`squareRoot(x)`
- 三角函数只有 `cos` / `sin`（没有 `tan` / `asin` / `acos`）

## 为什么值得做这件事

前三条发现，没有一条能从文档推出来：

- 文档说"`setUnitMemory` 改变内存"，没说**多赋值是顺序还是并行**
- 文档说"`isVisible` 隐藏单位"，没说**在 hiddenAction 里会抛异常**
- 文档列了 `alwaysSinglePress`，没说**它需要另外两个键配合**

而这三条恰好都是"写错了不报错、只是行为不对"或者"报错但不知道原因"的地方。

**这正是"盲人摸瞎"的部分**：键名可以查表，语义只能读源码。
